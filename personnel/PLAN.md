## Slice แรก — ทำเสร็จแล้ว: สรุปเวลาทำงานรายคน (ขาด/ลา/มา/สาย)

### วิธีดึงข้อมูล — **ดึงเมื่อต้องใช้ (lazy/on-demand)** ยืนยัน 2026-07-25
> **แก้จากแผนเดิมที่จะซิงก์ทุก 1 ชม.** — ผู้ใช้ท้วงว่าเป้าหมายคือ "สรุปเวลาทำงาน" ไม่ใช่
> กระดานสด ถ้าไม่มีใครเปิดดูก็ไม่ต้องดึง · เห็นด้วย: cron รายชั่วโมงดึงทิ้งเปล่าเป็นส่วนใหญ่
> (กลางคืน/เสาร์-อาทิตย์/วันหยุด) แถมต้องตั้ง pg_cron เพิ่ม = จุดที่พังเงียบได้อีกจุด

**หน้าสรุปเลือกเป็น "เดือน" (ยืนยัน 2026-07-25 — ผู้ใช้เสนอ)** → คิดทีเดียวยาวๆ ต่อเดือน
และ Jibble รับ `$filter` เป็นช่วงวันที่อยู่แล้ว → **ยิง API ครั้งเดียวได้ทั้งเดือน** ไม่ใช่ยิงทีละวัน
```
เปิดหน้าสรุป (เลือกเดือน)
  → อ่าน work_month_sync ของเดือนนั้น: ดึงครบถึงวันไหนแล้ว (synced_through)
      ครบถึงสิ้นเดือน (เดือนที่ผ่านมาแล้ว) → อ่านจาก Supabase ล้วน ไม่แตะ Jibble เลย ⚡
      ยังไม่ครบ → เรียก Supabase Edge Function ดึงช่วงที่ขาด (synced_through+1 → วันนี้)
            → Function แลก key เป็น token ที่ identity.prod.jibble.io/connect/token
            → ดึง TimeEntries ($filter ช่วงวัน + วน $skip เอง) → ยุบเป็นรายวัน
            → upsert work_attendance (unique staff+date) + อัปเดต synced_through
      → แล้วค่อยอ่านมาสรุป
```
**กติกาความนิ่งของข้อมูล (ปรับ 2026-07-25 ตามที่ผู้ใช้ระบุ):**
```
วันนิ่ง (final) = วันก่อนหน้า  OR  วันนี้ที่เลย 18:00 แล้ว
synced_through = วันนิ่งล่าสุดที่ดึงมาแล้ว (ไม่เกินสิ้นเดือนที่เลือก)
```
→ ก่อน 18:00 วันนี้ยังไม่นิ่ง จึงถูกดึงใหม่ทุกครั้งที่เปิดหน้า; แสดงสถานะที่รู้แล้วเป็น
มา/สาย/ลา ส่วนคนที่ยังไม่มีข้อมูลเป็น “รอครบวัน” และยังห้ามนับว่าขาด
→ หลัง 18:00 วันนี้นิ่งแล้ว **ไม่ต้องดึงซ้ำอีก** และเริ่มนับเข้ายอดสรุปตามปกติ
Jibble API key ยังอยู่ใน Supabase secrets ฝั่ง server เหมือนเดิม หน้าเว็บ public ไม่เห็น key
**ไม่ต้องใช้ pg_cron** — ตัดความซับซ้อนออกไปหนึ่งชั้น

**กติกาความสดของข้อมูล:**
- **วันที่ผ่านไปแล้วและเลย 18:00** → ข้อมูลนิ่ง (Jibble auto clock-out หมดแล้ว) cache ถาวร ไม่ดึงซ้ำ
- **วันนี้** → ยังไม่นิ่ง ดึงใหม่ทุกครั้งที่เปิดหน้า (แสดงป้ายว่าเป็นข้อมูลชั่วคราว)
- **ปุ่ม "ซิงก์ใหม่"** → ล้าง `synced_through` ของเดือนนั้น = ดึงใหม่ทั้งเดือนทับของเดิม
  **จำเป็นจริง** เพราะพบว่า Jibble ตั้ง `IsEditTimeEntriesAllowed = true` (แก้เวลาย้อนหลังได้)
  → ข้อมูลเดือนเก่าที่ cache ไว้อาจไม่ตรงกับ Jibble ถ้ามีคนไปแก้

**ตารางเพิ่ม `work_month_sync (year_month pk, synced_through date, synced_at)`**
ทำไมต้องมี: `work_attendance` เก็บเฉพาะคนที่มาลงเวลา → **"วันหยุดที่ดึงแล้วไม่มีใครมา" กับ
"วันที่ยังไม่เคยดึง" หน้าตาเหมือนกันเป๊ะ (ว่างเปล่าทั้งคู่)** ถ้าใช้เงื่อนไข "ไม่มีข้อมูล → ไปดึง"
ระบบจะวิ่งดึงวันหยุด/เสาร์-อาทิตย์ซ้ำ**ทุกครั้ง**ที่เปิดหน้า และไม่มีวันหยุดวิ่ง เพราะการดึงไม่เคย
ทำให้ตารางมีข้อมูล → ตารางนี้คือ "สมุดจดว่าถาม Jibble ไปแล้ว" แยกจาก "คำตอบว่าใครมาบ้าง"
· เดิมออกแบบเป็นรายวัน (365 แถว/ปี) → **เปลี่ยนเป็นรายเดือน (12 แถว/ปี)** เพราะหน้าสรุป
เลือกเป็นเดือนอยู่แล้ว

**เกร็ด Jibble ที่กระทบตรรกะ (ยืนยันแล้ว):** Jibble ตัดเวลาสุดท้าย **18:00** — ใครไม่ logout
ระบบ auto-logout ให้เองตอน 18:00 → ข้อมูลของวันจะ "นิ่ง/final" หลัง 18:00 → การซิงก์รายชั่วโมง
ระหว่างวันให้ค่า provisional (ใช้โชว์ "วันนี้ใครมา/สาย" แบบสด) ส่วนสรุป ขาด/สาย รายเดือนที่เป็น
ทางการควรอ่านสถานะของวันหลัง 18:00

แต่ **Supabase Edge Function = backend ฝั่ง server** เก็บ Jibble key ปลอดภัยได้ → หน้าเว็บ public
ไม่เห็น key เลย · (ทางเลือกสำรอง A = ครู export ไฟล์มาวางเอง ใช้ backfill ข้อมูลย้อนหลัง/กรณี API ล่ม)

### กติกาที่ยืนยันแล้ว
- **การลา** = กรอกเองในระบบเรา (ใบลากระดาษ ไม่อยู่ใน Jibble) — **มีครึ่งวัน** (เช้า/บ่าย น้ำหนัก 0.5)
- **มาสาย** = เรา **ตั้งเวลา cutoff กลางเอง** (config เช่น 07:45) → เวลาเข้าหลัง cutoff = สาย
- **ขออนุญาตเข้าสายรายคน (ยืนยันแล้ว)** — ครูบางคนได้รับอนุญาตให้เข้าสายได้ตามเวลาที่โรงเรียน
  กำหนดเป็นรายคน โดย**ไม่นับว่าสาย** → ต้องมีฟิลด์ `allowed_late_time` (เวลา cutoff เฉพาะคนนั้น,
  nullable) ในตาราง `staff` → ถ้ามีค่า ใช้ค่านี้แทน cutoff กลางในการตัดสินสายของคนนั้น
  (เข้าก่อน `allowed_late_time` = ไม่สาย, เข้าหลัง = สาย) · เผื่ออนาคตอาจต้องมีช่วงวันที่มีผล
  แต่ slice แรกทำเป็นค่าคงที่รายคนไปก่อน
- **ขาด** = ไม่มีเวลาเข้าใน Jibble ในวันทำงาน (และไม่ได้ลา และไม่ใช่คนอนุโลม)
- **ปฏิทินวันหยุด — ใช้ของ Jibble (สรุปสุดท้าย 2026-07-25 · ไม่ต้องทำตารางเอง)**
  ประวัติการตัดสินใจ: (1) เดิมเข้าใจผิดว่า "Jibble มีเฉพาะวันทำงาน ไม่ต้องทำปฏิทิน"
  (2) แก้เป็น "ต้องทำตาราง `school_holidays` เอง" (3) **สรุปจริง: Jibble ตั้งวันหยุดได้ และ
  API ดึงออกมาได้ → ตัด `school_holidays` ทิ้ง ใช้ Jibble เป็นแหล่งเดียว** ครูกรอกที่เดียวจบ
  ไม่มีข้อมูล 2 ที่ให้ขัดกัน
  - ผู้ใช้สร้างปฏิทิน **"วันหยุดโรงเรียนเจริญศึกษา"** (default) แล้ว 2026-07-25
  - เลือก **Add manually ไม่ import ปฏิทินไทย** (ยืนยันแล้ว: โรงเรียนไม่ได้หยุดตามราชการทุกวัน
    ถ้า import จะได้วันหยุดที่ไม่จริงปนมา แล้วระบบจะไม่นับคนขาดในวันที่ครูมาทำงานจริง)
  - **ข้อแลกเปลี่ยน**: วันหยุดที่เพิ่มเอง **ไม่ทำซ้ำอัตโนมัติทุกปี** ต้องเพิ่มใหม่ทุกปีการศึกษา
    ถ้าลืม → วันนั้นจะขึ้นว่าครูขาดกันทั้งโรงเรียน → **หน้าสรุปต้องมีตัวเตือน** "วันนี้ไม่มีใคร
    มาเลยแต่ไม่ได้ตั้งเป็นวันหยุด ตรวจสอบ?"
  - ไม่ต้องใส่เสาร์-อาทิตย์ในปฏิทิน (ดูตารางงานด้านล่าง — Jibble รู้อยู่แล้วว่าทำงาน จ-ศ)
  - **ปิดเทอม ≠ ครูหยุด** — ปิดเทอมปิดแค่นักเรียน **ครูยังมาทำงานตามปกติ** โรงเรียนหยุดให้ครู
    จริงแค่ **1 สัปดาห์** เท่านั้น → ห้าม auto-ถือว่าช่วงปิดเทอมทั้งช่วงเป็นวันหยุด
- **วันที่คนลงเวลาน้อยผิดปกติ → ขึ้นธงให้คนตรวจ ไม่ตัดสินเอง** (ยืนยันแล้ว)
  เช่น วันที่มีคนมาแค่ 2-3 คน (เวร/มาทำงานวันหยุด) ระบบต้องไม่เดาว่าเป็นวันหยุดหรือวันทำงาน
  ให้แสดงเป็นรายการ "วันที่ต้องตรวจสอบ" ให้ admin ยืนยันว่าวันนั้นคือวันทำงานหรือวันหยุด
- ระบบรองรับ **คนได้รับการอนุโลม** ผ่านธง `exempt` ในตาราง `staff`
  (คนที่ exempt ไม่ขึ้นว่าขาด/สายเลย นับมาเสมอในวันทำงาน) — ข้อมูลปัจจุบัน **0 คน**

> **โครงสร้างตารางฉบับสมบูรณ์อยู่ที่หัวข้อ "ร่างโครงสร้างตาราง" ด้านล่าง**
> (ร่างชุดแรกที่เคยอยู่ตรงนี้ถูกลบแล้ว เพราะยังไม่มี `work_month_sync`/`leave_quotas`/
> `academic_years`/`work_holidays`/`work_schedule` — อ่านของเก่าแล้วจะเข้าใจผิด)

### โครงสร้างข้อมูลจริงจาก Jibble API (สำรวจแล้ว 2026-07-25)
```
GET https://workspace.prod.jibble.io/v1/People
  id, fullName, email, code (เช่น TA-1, อป-1), status ('Joined'/'Removed'), role ('Member'/'Owner'),
  workStartDate, ICultureSettings/TimeZone='Asia/Bangkok'
  ITimeTrackingSettings/AutomaticOutAtTime = '18:00:00' ทุกคน  ← ตรงกับที่ผู้ใช้บอก
  scheduleId = null ทุกคน  ← Jibble ไม่รู้เวลาเข้างานที่ควรเป็น → ยืนยันว่าต้องตั้ง cutoff เอง

GET https://time-tracking.prod.jibble.io/v1/TimeEntries   (OData: $select/$filter/$top/$orderby)
  personId (→ People.id), type ('In'/'Out'), belongsToDate ('2026-07-24') ← คีย์วันทำงาน,
  localTime ('2026-07-24T07:39:27+07:00'), time (UTC), status ('Active'),
  clientType ('Android'/'IOS' = คนกดเอง, 'AutoOut' = ระบบเด้งออก 18:00), isAutomatic
```
**เป็น event ทีละครั้ง ไม่ใช่สรุปรายวัน** → Edge Function ต้องยุบเป็นรายวันเอง:
`เวลามา = In แรกสุดของ (personId, belongsToDate)` · `เวลากลับ = Out ท้ายสุด`
ตัวอย่างจริง 24 ก.ค.: เข้างานกันราว 07:32–07:39, หลายคนออกด้วย AutoOut 18:00

**⚠ Jibble ไม่มีแถวของคนที่ไม่มา** — คนขาด = ไม่มี record เลย → ตัดสิน "ขาด" ต้องเอา

## ข้อมูลจริงที่สำรวจได้ (2026-07-25 รอบ 4) — ใช้เป็นฐานออกแบบ

```

วันหยุดในปฏิทิน:  1 วัน (2026-07-28 วันเฉลิมพระชนมพรรษาฯ) — ผู้ใช้เพิ่งใส่ทดสอบ
รูปแบบ 45 วันล่าสุด:
  จันทร์–ศุกร์   มา 16–20 คน   ← วันทำงาน (ตรงกับ Schedules จ-ศ)
  เสาร์–อาทิตย์  มา  1–2 คน    ← เวร/มาทำงานวันหยุด → ต้องขึ้นธงให้คนตรวจ ไม่เดาเอง
```
→ วันทำงานปกติมีคนไม่มา 0–4 คน = ยอด "ขาด/ลา" ที่ระบบต้องคำนวณ

### ⚠️ ข้อมูล "เวลาออก" ใช้ไม่ได้จริง — ยืนยันด้วยตัวเลข (2026-07-25)
โรงเรียนเลิก **16:30** แต่ตั้ง Jibble ให้ **auto clock-out 18:00** เป็นตัวดักเผื่อครูลืมกด logout
(ผู้ใช้อธิบายเอง) → `lastOut = 18:00` + `clientType = 'AutoOut'` **แปลว่า "ลืม logout"
ไม่ใช่ "ทำงานถึง 18:00"**

ตัวเลขจริง 45 วัน: **Out ทั้งหมด 488 ครั้ง — เป็น AutoOut 392 ครั้ง (80%)** กดเองแค่ 20%
และมีอย่างน้อย **8 คนที่ลืม 100%** (ไม่เคยกด logout เองเลยสักวัน)

**ผลต่อการออกแบบ:**
- ❌ **ห้ามใช้ `last_out` คำนวณชั่วโมงทำงาน/เวลากลับ** — จะได้ 18:00 เกือบทุกคนทุกวัน ไร้ความหมาย
- ✅ **ไม่กระทบ slice แรก** — ขาด/ลา/มา/สาย ใช้แค่ **เวลาเข้า (first_in)** ซึ่งครูกดเองจริง
- ⚠️ **รายงาน "ใครลืม logout" ยังไม่ควรทำตอนนี้** — จะติดธงเกือบทุกคน ใช้จับผิดใครไม่ได้
  ถ้าโรงเรียนอยากใช้จริงต้องแก้พฤติกรรมก่อน (เช่นเตือนตอน 16:30) แล้วค่อยวัดผล
- ยังเก็บคอลัมน์ `auto_out` ไว้ใน `work_attendance` (ข้อมูลมีอยู่แล้ว ไม่เสียหาย เผื่อใช้ทีหลัง)

**`Timesheets` (time-attendance) ใช้ได้ แต่ตัดสินใจไม่ใช้**: ต้องส่ง `date` + `endDate`
คืน `daily[]` ที่มี `date, firstIn, lastOut, trackedHours` (Jibble ยุบรายวันให้แล้ว) —
**เลือกใช้ `TimeEntries` แล้วคำนวณเองแทน** เพราะต้องคุมกฎเอง (คนอนุโลม / allowed_late_time
รายคน / การลาที่อยู่ในระบบเรา) และไม่อยากผูกกับพฤติกรรมที่ Jibble ไม่ได้ประกาศชัด

### ⚠️ กับดักทางเทคนิคที่เจอจริง (ต้องระวังตอนเขียน Edge Function)
- **Jibble ไม่ส่ง `@odata.nextLink`** — ดึง `$top=1000` แล้วได้ 1000 แถวและหยุด ข้อมูลที่เหลือ
  **หายเงียบๆ ไม่มี error** (รอบ 4 ข้อมูล 17–25 ก.ค. หายไปเพราะเหตุนี้)
  → ต้องวนหน้าเองด้วย **`$skip`** จนกว่าจะได้น้อยกว่า `$top` แล้วค่อยหยุด
- `$filter=belongsToDate ge YYYY-MM-DD` ใช้ได้จริง (ยืนยันแล้ว) → ดึงเฉพาะช่วงที่ต้องการได้
- SSL: python.org Python บน macOS ใช้ไม่ได้ (CERTIFICATE_VERIFY_FAILED) ต้องใช้ `/usr/bin/python3`
  หรือรัน `Install Certificates.command` — เรื่องเครื่อง dev เท่านั้น ไม่กระทบ Edge Function

```sql
staff                      -- บุคลากรทุกคน (รวมคนไม่มีบัญชีล็อกอิน)
  id, full_name, position, staff_type, email,
  jibble_person_id unique  -- = Jibble People.id (จับคู่ตรงๆ ไม่ต้องเทียบชื่อ)
                           -- nullable เพื่อรองรับบุคลากรที่เพิ่มเองและไม่มีบัญชี Jibble
  jibble_code              -- = People.code เช่น TA-1

  exempt boolean           -- อนุโลม ไม่ต้องลงเวลา ถือว่ามาเสมอ
  allowed_late_time time   -- อนุญาตเข้าสายถึงเวลานี้ (override เวลากลาง) nullable
  user_id                  -- ผูกกับ auth.users ถ้ามีบัญชี (nullable)

work_attendance            -- สรุปรายวัน (Edge Function ยุบจาก TimeEntries)
  staff_id, work_date, first_in, last_out, first_in_local,
  auto_out boolean,        -- ออกด้วย AutoOut 18:00 หรือกดเอง
  synced_at
  unique(staff_id, work_date)   -- upsert ซ้ำได้ ไม่เกิดแถวซ้ำ

work_holidays              -- cache วันหยุดจาก Jibble CalendarDays
  holiday_date pk, name, is_short_day, jibble_id, synced_at

work_schedule              -- cache ตารางงานจาก Jibble Schedules
  weekday pk (1=จ..7=อา), start_time, end_time, is_working_day

staff_leaves               -- การลา (กรอกเองในระบบเรา — Jibble ไม่มีข้อมูล)
  staff_id, start_date, end_date, leave_type (ป่วย/กิจ/พักผ่อน/คลอด),
  day_portion ('full'|'morning'|'afternoon'), reason, created_by

leave_quotas               -- สิทธิ์วันลาต่อปีการศึกษา
  year ('2569'), leave_type, days numeric
  -- ✅ ตัวเลขจริง (ยืนยัน 2026-07-25):  ลากิจ 7 วัน · ลาป่วย 30 วัน  ต่อปีการศึกษา
  -- ✅ ลาคลอด 45 วัน — **ผู้ใช้ยืนยันแล้ว 2026-07-25** (ตอนแรกบอก "รู้สึกว่า" แล้วยืนยันภายหลัง)
  -- ประเภทที่ไม่มีแถวในตารางนี้ = ไม่มีโควตา (ไม่แสดง "เหลือกี่วัน")
  -- ⚠ ยังไม่ยืนยันว่าโควตาต่างกันตามประเภทบุคลากรไหม (ครู vs ธุรการ vs นักการ)

academic_years             -- วันเริ่มปีการศึกษา (ตั้งค่าได้ — ผู้ใช้ระบุว่า "อาจเปลี่ยนแปลงได้")
  year pk ('2569'), start_date date   -- เช่น 2569 → 2026-05-16
  -- รอบปี = [start_date ปีนี้ , start_date ปีหน้า)  ← ครอบเมษายนไว้ในปีก่อนหน้าอัตโนมัติ
  -- แก้ปัญหา "เมษายนนับเข้าปีไหน" ได้ในตัว ไม่มีวันไหนตกหล่น

work_month_sync            -- จดว่าดึงถึงไหนแล้ว (กันดึงซ้ำ + แยกวันหยุดออกจากวันที่ยังไม่ดึง)
  year_month pk ('2026-07'), synced_through date, synced_at
  -- synced_through ห้ามเลยเมื่อวาน → วันนี้ถูกดึงใหม่ทุกครั้งอัตโนมัติ

hr_settings                -- late_grace_minutes (ค่าเริ่มต้น 5) ฯลฯ
                           -- ⚠ ต้องมีหน้าให้ admin แก้ค่านี้ได้เอง (ยืนยันแล้ว) ไม่ hardcode
jibble_sync_log            -- started_at, finished_at, ok, rows, message
```

### ตรรกะสรุปสถานะ (staff × วัน) — คำนวณตอนแสดงผล ไม่ store
```
1. ไม่ใช่วันทำงาน (work_schedule) หรือเป็นวันหยุด (work_holidays) → "หยุด" ไม่นับ
2. วันในอนาคต                                                   → "รอครบวัน"
3. staff.exempt = true                                          → "มา" เสมอ
4. มี staff_leaves ครอบวันนั้น                                   → "ลา" (เต็มวัน/ครึ่งวัน 0.5)
5. มี work_attendance:
     cutoff = staff.allowed_late_time  ถ้าไม่มีใช้  schedule.start_time + late_grace_minutes
            = ค่าเริ่มต้น 07:45 + 5 นาที = 07:50  (ยืนยันแล้ว · แก้ค่าได้ในหน้าตั้งค่า)
     first_in_local <= cutoff → "มา"        first_in_local > cutoff → "สาย"
6. วันนี้ก่อนเวลาปิดวันและยังไม่มีเวลาเข้า                        → "รอครบวัน" ห้ามนับว่าขาด
7. ไม่มี work_attendance เลยหลังปิดวัน                            → "ขาด"

ธงเตือน: วันทำงานที่มีคนมาน้อยผิดปกติ (เช่น < 50% ของ staff ที่ active)
        → ขึ้นรายการ "ต้องตรวจสอบ" ว่าเป็นวันหยุดที่ลืมตั้งหรือไม่ (ไม่ตัดสินเอง)
```

```
วันนี้ หลัง 18:00  → นับเข้ายอดปกติเหมือนวันอื่นทุกประการ
```
ไม่งั้นผู้บริหารเปิดดูตอนเช้าจะเห็นครูครึ่งโรงเรียนขึ้นแดงว่าขาด ทั้งที่ยังไม่ถึงเวลา

**ผลต่อกติกาการซิงก์ (ทำให้ง่ายลง)** — นิยาม "วันที่นิ่งแล้ว" รวมศูนย์เป็นข้อเดียว:
```
วันนิ่ง (final) = วันก่อนหน้า  OR  วันนี้ที่เลยเวลา 18:00 ไปแล้ว
```
→ `synced_through` เลื่อนถึงวันนี้ได้เมื่อเลย 18:00 → **หลัง 18:00 ไม่ต้องดึงวันนี้ซ้ำอีก**
(เดิมออกแบบว่า "วันนี้ดึงใหม่ทุกครั้งเสมอ" — ตอนนี้ดึงซ้ำเฉพาะช่วงก่อน 18:00 เท่านั้น)
· เวลา 18:00 มาจากค่า `AutomaticOutAtTime` ของ Jibble — **ควรอ่านจาก API ไม่ hardcode**
  (ทุกคนตั้ง 18:00:00 เหมือนกันหมด ยืนยันจากข้อมูลจริงแล้ว)

**สะสม = รอบปีการศึกษา (พ.ค.–มี.ค.)** ใช้ตรรกะเดียวกับรายเดือน แค่ขยายช่วง
→ ⚠️ ถ้าเปิดดูสะสมทั้งปี ระบบต้องมีข้อมูลครบทุกเดือนในปีนั้น = อาจต้องดึง Jibble หลายเดือนรวด
   ครั้งแรกที่เปิด (ช้าได้) → ต้องมีตัวบอกสถานะ "กำลังดึงข้อมูล..." ไม่ให้ผู้ใช้คิดว่าค้าง

**ใช้ component เดียวกับ "ข้อมูลการทำงานของฉัน"** — มุมมองรายคนเหมือนกันเป๊ะ ต่างแค่ขอบเขต
สิทธิ์ (ผู้บริหารเลือกคนไหนก็ได้ / ครูเห็นแต่ของตัวเอง) → เขียนครั้งเดียวใช้ 2 ที่

### หน้า "ข้อมูลการทำงานของฉัน" (ยืนยัน 2026-07-25 — ผู้ใช้ท้วงว่าแผนเดิมขาดไป)
แผนเดิมมีแต่**มุมผู้บริหาร** (ภาพรวมทั้งโรงเรียน) แต่บุคลากรต้องตรวจสอบของตัวเองได้ด้วย
ว่าขาดไปกี่วัน ลาไปกี่วัน แยกประเภท (ลากิจ/ลาป่วย) และเหลือสิทธิ์อีกเท่าไหร่
```
เดือนนี้              สะสมทั้งปีการศึกษา
  มา / สาย / ขาด        มา / สาย / ขาด
  ลาป่วย / ลากิจ        ลาป่วย X (เหลือ Y) · ลากิจ X (เหลือ Y)   ← เทียบ leave_quotas
```
- **ใช้ข้อมูลชุดเดิมทั้งหมด ไม่ต้องเพิ่มตาราง** (นอกจาก `leave_quotas`) — เป็นแค่มุมมองใหม่
- **รอบนับสะสม = ปีการศึกษา** ตามช่วง `[วันเริ่มปีนี้, วันเริ่มปีถัดไป)` ยืนยันแล้ว
  เดือนเมษายนจึงอยู่ในปีการศึกษาก่อนหน้าโดยอัตโนมัติ
- **สิทธิ์การเห็น: ครูเห็นของตัวเองเท่านั้น** (ยืนยันแล้ว) — admin/ผู้บริหารเห็นภาพรวมทั้งโรงเรียน
  → RLS: `staff.user_id = auth.uid()` สำหรับครู, `is_admin()` เห็นทั้งหมด
  → บุคลากรที่ไม่มีบัญชีล็อกอิน (ธุรการ/นักการ) ดูเองไม่ได้ ต้องให้ admin เปิดให้ดู/พิมพ์ให้

## ⭐ ระบบสิทธิ์ระดับฝ่าย (ส่วนกลาง — กระทบทั้งระบบ ไม่ใช่แค่ฝ่ายบุคคล)

> ผู้ใช้กำหนดโมเดลนี้เอง 2026-07-25 · เดิมผมเสนอแค่ธง `can_manage_hr` เฉพาะงานบุคคล
> ผู้ใช้ขยายให้เป็นระบบกลางครอบทั้ง 4 ฝ่าย — ดีกว่าและใช้กลไกเดียวกันได้หมด
> **หมายเหตุ: ส่วนนี้เป็นการออกแบบระดับระบบ ควรย้ายไปเอกสารกลางเมื่อเริ่มทำฝ่ายอื่น**

**โมเดล:** `(ระบุว่าอยู่ฝ่ายไหน) + (admin กดอนุญาต)` → มีอำนาจเท่า admin **เฉพาะหน้าของฝ่ายนั้น**
ถ้า admin ตั้ง "ไม่อนุญาต" → แม้ระบุว่าอยู่ฝ่ายนั้นก็ทำอะไรไม่ได้ (ตัวอย่างที่ผู้ใช้ยกมา:
"นายเอ ฝ่ายวิชาการ สิทธิ์ ไม่อนุญาต → ดำเนินการในส่วนวิชาการไม่ได้")

```sql
user_departments                              -- คนหนึ่งอยู่ได้หลายฝ่าย (ยืนยันแล้ว)
  user_id     uuid → auth.users on delete cascade
  department  text check in ('วิชาการ','บุคลากร','การเงิน','บริหารทั่วไป')
  granted     boolean not null default false  -- ⭐ admin ต้องกดอนุญาตก่อนจึงมีผล
  granted_by, granted_at
  primary key (user_id, department)

has_department(dept)  -- security definer เหมือน is_admin()/can_edit_subject()
  = is_admin() OR exists(user_departments where user_id=auth.uid()
                         and department=dept and granted)
```

### ขอบเขตสิทธิ์: **แก้ได้แต่ลบไม่ได้** (ยืนยันแล้ว)
| การกระทำ | admin | ฝ่ายที่ได้รับอนุญาต | ครูทั่วไป |
|---------|-------|-------------------|----------|
| อ่าน | ✅ | ✅ | ✅ (บางหน้าเห็นเฉพาะของตัวเอง) |
| เพิ่ม / แก้ไข | ✅ | ✅ | ตามกติกาเดิมของแต่ละฝ่าย |
| **ลบ** | ✅ | ❌ **สงวนไว้ที่ admin เท่านั้น** | ❌ |

→ pattern ของ policy ตารางใหม่: `INSERT/UPDATE = has_department('บุคลากร')`,
`DELETE = is_admin()`
→ **ผลข้างเคียงที่ต้องรับรู้**: ธุรการคีย์ใบลาผิด จะลบเองไม่ได้ ต้องแก้ให้ถูก (แก้ได้) หรือ
เรียก admin ลบ — ยอมรับได้เพราะแลกกับการกันข้อมูลหายถาวร

1. **ตอนนี้**: สร้าง `user_departments` + `has_department()` แล้วใช้กับ **ตารางใหม่ของฝ่าย
   บุคคลเท่านั้น** — **ไม่แตะ policy เดิมของวิชาการแม้แต่ตัวเดียว** ปลอดภัย 100%
2. **ทีหลัง (งานแยก)**: ยกฝ่ายวิชาการมาใช้ `has_department('วิชาการ')`

### ✅ ขอบเขตการยกฝ่ายวิชาการ = **ตัวเลือก C** (ยืนยัน 2026-07-25)
สำรวจ schema จริงแล้ว: policy ทั้งหมด **83 ตัว** — ~67 จุดใช้ `can_edit_*` (owner-based)
ซึ่ง**ทุกตัวไล่กลับไปเรียก `can_edit_subject()` ตัวเดียว** (`schema.sql:435`) ส่วน ~14 ตัว
ใช้ `is_admin()` · มี `_delete` 13 ตัว + `_write` แบบ for-all 14 ตัว

| ทางเลือกที่พิจารณา | งานที่ต้องทำ | ผล |
|-----------------|-------------|-----|
| A: ฝ่าย = admin เต็ม (ลบได้) | แก้ `can_edit_subject()` 1 ฟังก์ชัน | ตกไป — ลบวิชา = คะแนนหายหมด |
| B: แก้ได้ไม่ลบ ครอบทุกวิชา | แตะ **27 policies** (แยก delete ออกจาก for-all) | ตกไป — เสี่ยงเกินประโยชน์ |
| **C: ให้เฉพาะที่ตอนนี้เป็น admin-only** | แตะ **~5 policies** | ✅ **เลือกอันนี้** |

**C ให้สิทธิ์อะไรบ้าง** (กับคนที่อยู่ฝ่ายวิชาการและได้รับอนุญาต แต่ไม่ใช่ admin):
```
เปลี่ยนจาก ❌ → ✅ :  สร้างวิชาใหม่ · แก้ข้อมูลวิชา · เพิ่ม/แก้นักเรียน · ขึ้นปีการศึกษาใหม่
คงเดิม ✅       :  แก้โครงสร้าง/คะแนน "วิชาตัวเอง" (owner-based เดิม ไม่แตะ)
คงเดิม ❌       :  แก้โครงสร้าง/คะแนน "วิชาคนอื่น"  ·  ลบวิชา
```
**ทำไม C ถึงงานน้อย**: `subjects_delete` เป็น policy แยกอยู่แล้ว → คงเป็น admin-only ต่อไปได้เลย
**ไม่ต้องแตก `_write` แบบ for-all ออกเป็น delete แยกเลย** และไม่แตะ 67 จุด owner-based
→ ครูที่ใช้งานอยู่ทุกวันนี้ไม่ได้รับผลกระทบ

**policy ที่ต้องแก้ (ประมาณ 5 ตัว)**: `subjects_insert`, `subjects_update`, `students_write`,
`student_year_placements_write`, `app_settings_write` → เปลี่ยนจาก `is_admin()` เป็น
`is_admin() OR has_department('วิชาการ')` · ⚠️ ตัวที่เป็น `for all` ต้องดูว่าจะยอมให้ลบด้วยไหม
(ถ้าไม่ ต้องแตกเฉพาะตัวนั้น) — ตรวจทีละตัวตอนลงมือ ห้ามเหมา
**ข้อจำกัดที่ยอมรับแล้ว**: ครูลาออกกลางเทอมแล้วต้องกรอกคะแนนแทน → ยังต้องพึ่ง admin

### ธีม/หน้าตา: **ใช้ของฝ่ายวิชาการทั้งหมด** (ยืนยัน 2026-07-25)
ผู้ใช้เลือก "เอาธีมสีและรูปแบบของวิชาการเลย จะได้มาแนวเดียวกัน" — **ไม่ทำสีประจำฝ่าย**

  ไม่ใช่ของฝ่ายวิชาการ แต่การรีเนมกระทบ CSS 10 หน้าที่ใช้งานจริงโดยไม่ได้ประโยชน์ทางสายตา
  → **ใช้ชื่อเดิมต่อไปในทุกฝ่าย** (แลกชื่อที่ดูแปลกนิดหน่อยกับความเสี่ยงศูนย์)

### จังหวะการซิงก์จาก Jibble (สรุปครบทั้ง 4 ชุดข้อมูล) — ยืนยัน 2026-07-25
**ไม่มีการดึงเบื้องหลังเลย — ดึงเมื่อมีคนเปิดดูเท่านั้น**

| ข้อมูล | ดึงตอนไหน | เหตุผล |
|-------|----------|--------|
| **TimeEntries** เวลาเข้า-ออก | เปิดหน้าสรุป/ข้อมูลของฉัน → เฉพาะวันที่ยังไม่มีในเดือนนั้น **+ วันนี้ดึงใหม่เสมอ** | เปลี่ยนทุกวัน แต่วันเก่านิ่งหลัง 18:00 |
| **CalendarDays** วันหยุด | พ่วงไปกับการซิงก์เดือน **ทุกครั้ง** | เล็กมาก (ไม่กี่แถว) + ถ้าครูเพิ่งเพิ่มวันหยุดจะเห็นทันที |
| **Schedules** ตารางงาน | พ่วงไปกับการซิงก์เดือน + ตอนเปิดหน้าตั้งค่า | นานๆ เปลี่ยนที แต่ถ้าเปลี่ยนแล้วไม่รู้ = คำนวณสายผิดทั้งระบบ |
| **People** รายชื่อ | เปิดหน้าทะเบียนบุคลากร + ปุ่ม "ดึงรายชื่อจาก Jibble" | มีคนเข้า/ออกนานๆ ที |

```
เปิดหน้าสรุปเดือน  → ข้อมูลครบแล้ว: ไม่แตะ Jibble เลย (เร็ว)
                   → ขาด/มีวันนี้:  ดึงเฉพาะที่ขาด + วันหยุด + ตารางงาน
เปิดทะเบียนบุคลากร → ดึงรายชื่อมาเทียบ (มีคนใหม่ไหม / ใครลาออก)
ปุ่ม "ซิงก์ใหม่"    → ดึงทับทั้งเดือน (ใช้ตอนมีคนแก้เวลาย้อนหลังใน Jibble)
```
